# ADR-0001: Evidence-first document intelligence redesign

- Status: accepted for incremental implementation
- Date: 2026-11-07
- Scope: Phase 1 tender intake, requirement extraction, human review, and export

## Context

The application is a single Next.js/TypeScript service. `apps/web/app/actions.ts` owns most of the upload pipeline: PDF validation and parsing, page/OCR preparation, section routing, table interpretation, model calls, coverage accounting, quote verification, and response-sheet construction. The modules around it provide useful boundaries, but the orchestration remains broad and in-process. Browser state holds the uploaded document and review edits; there is no database, worker, shared queue, or cross-instance rate limiter.

PDF.js is the production parser. It supplies selectable text, positioned text items, page geometry, and vector drawing operators. `source-document.ts` preserves the document fingerprint, page-local text blocks, source references, and selected table structure. `vector-table.ts` reconstructs rows and cells from drawing geometry. `local-ocr.ts` uses Poppler rendering and Tesseract when available; `ocr-routing.ts` flags likely mixed/scanned pages. Layout interpretation and requirement classification use the configured model. Deterministic code verifies source text and locations, tracks extraction/coverage states, and projects independently answerable rows into review and exports. The model is not the source of citation geometry or verified text.

This design has produced useful capabilities, but a six-document run on `dd0c2c7` completed only two analyses within the local 295-second request limit. Routing also left many pages unaudited. A response matrix with source-matched rows therefore does not establish document completeness.

## Decision

Keep the product in TypeScript and retain PDF.js as the production parser while the redesign is measured. Evolve the existing pipeline through small, testable boundaries instead of replacing the application wholesale.

Treat a tender as a canonical, source-preserving inventory before interpreting it. The inventory should retain source document/version identity, physical page, exact text or OCR transcript, text and cell geometry when known, table candidates, OCR confidence, and unknown/approximate markers. Interpretation creates atomic requirement proposals that point back to inventory regions. Independent deterministic checks then measure grounding, completeness, numeric fidelity, and recoverable omissions. A human-reviewed requirement set projects into the editable response matrix and its exports without combining independent response decisions.

Requirement citations carry stable page-scoped source element IDs in addition to offsets and locations. Native text references link every parser text block overlapped by the exact source span; table references link the table, row, and cell; OCR references link only OCR regions containing an exact transcript match. A visual transcription without a deterministic text-to-region match keeps its geometric evidence approximate and does not receive a fabricated text element link. These are parser element IDs, not semantic paragraph/list/section IDs; hierarchy reconstruction remains a separate open step.

Before routing, the current runtime builds detected vector-table row candidates for every page with supported vector geometry, then checks the assembled source inventory for every physical page in order, exact native text-block offsets, unique parser element IDs, valid OCR-to-image references, and consistent table/row/cell relationships. Successful analyses expose this as a structural inventory check in the review ledger. Table geometry remains heuristic and may miss or combine tables; this gate detects malformed or incomplete parser output, not whether all visual regions, paragraphs, tables, or technical obligations were recognized.

Each detected raster image region now records its OCR disposition independently: not targeted, selected but not attempted with a skip reason, attempted with text found, attempted with no text, or failed. OCR regions linked to an image region must agree with the image region's `text-found` state. The review coverage ledger shows per-page counts, so a page-level OCR success cannot imply that every detected region was OCR-covered. Full-page OCR on scan-only pages may not link text to individual image operators; those image regions remain not targeted and the reviewer must use the page-level OCR status and visual evidence.

The page-routing pass may also propose cross-section inconsistencies, such as different equipment subjects in a tender title and a compliance annexure. A deterministic boundary checks each quoted side against its claimed page transcript before surfacing a warning; verified proposals mark and route both pages for review without choosing an authority. The detector is model-assisted and sees bounded page-group excerpts, so it is not an independent consistency oracle and can miss conflicts across groups or outside the supplied excerpts. The Saha example is recorded as unresolved evidence, not as a live-model detection result.

Page routing now returns a per-page `relevant`, `possibly_relevant`, or `excluded` disposition with a source-grounded reason. Relevant pages enter source extraction/review even when no section range was returned; possibly relevant pages enter deeper inspection while staying explicitly unresolved; exclusion is reported only when a reason is supplied. Missing dispositions remain `unrouted`, never implicitly excluded, and now also enter extraction. These classifications are model judgments over bounded excerpts, not completeness proof, and clipped context should remain a review concern.

Pages marked uncertain, including `possibly_relevant` dispositions and verified conflict pages, now also enter the normal source extraction and page-coverage audit path. Their routing disposition remains uncertain in the ledger and review note; extraction does not convert uncertainty into a relevance decision. This adds deeper inspection while keeping the unresolved state visible. It does not automatically select pages classified as explicitly excluded or pages with no routing disposition.

Text-page omission auditing now groups source pages into requests targeting at most 60,000 estimated characters and four pages, with a hard 180,000-character single-page/request cap. It runs at most eight batches per analysis and up to three concurrently. Every page begins as audit-incomplete; oversized pages, pages beyond the batch budget, failed requests, or invalid page references remain explicitly incomplete while successful batches still contribute validated recovery candidates. This prevents one oversized combined input from skipping all text-page audits, but it does not guarantee every page is audited or make analysis resumable.

In the visual compliance-sheet fallback, all three overlapping image regions for a page are now sent together for extraction, then together in a separate omission-audit call. Model outputs must identify which region supports each row; the deterministic path splits them back into region-scoped results and treats missing/invalid region indices as incomplete. This lowers the visual extraction/audit request count from six to two per page without merging extraction with verification. It increases the images/context in an individual request and still operates within the synchronous request deadline; no live before/after latency or recall claim has been measured.

Visual extraction now groups up to two selected PDF pages into one request while keeping page-specific column maps and binding each returned candidate to a validated parent page. Missing, duplicate, out-of-batch, or invalid-region results fail the affected batch closed. This further reduces extraction request count but does not batch the separate page-image audits. A fresh run at `00f51e3` on the hash-verified IIT Guwahati tender reached the 270-second deadline during extraction, with the last captured counters at four of five. The monitor did not retain the progress message, so this count cannot be attributed to vector-table versus visual extraction. No response sheet or coverage metrics were returned. The live result therefore does not show improved completion, latency, or quality. Bounded request batches are not resumable processing; future work must preserve successful source-linked page results and mark all unfinished extraction/audit states explicitly before exposing partial output.

A second isolated run with fixed progress messages retained reached the 270-second deadline at `d793802`. It completed document inventory and routing, then spent the remainder of the request in sequential vector-table inspection: four of five pages had completed at 212.3 seconds, and no response sheet was returned by 270.1 seconds. The code awaits each vector page's model classification and row-level semantic audits before starting the next page. This identifies sequential vector-page work as a concrete throughput target; parallelization must preserve schedule-specific column maps, source-row identity, deterministic page order, and per-row audit-incomplete states.

The parallel-inspection implementation is limited to vector pages that each visibly repeat the already-verified initial column headers; pages without that evidence, including changed layouts and continuations, retain source-ordered processing so they inherit the preceding verified map. Page classification can overlap up to the model client's per-analysis limit, while the analysis-wide source-row audit cap is consumed in page order. A scripted three-page contract verifies peak classification concurrency of three, stable requirement order and source-cell links, and audit request order. Of three subsequent runs on the hash-verified IIT Guwahati tender, the two runs with per-page counters reported completion one page at a time, confirming they used serial fallback because at least one selected page did not repeat the initial headers. Vector inspection finished at 142.4 seconds in one run and 149.4 seconds in another, but the runs selected five and four pages respectively and neither produced a response sheet; they do not isolate a causal speedup. The recorded runs and their limits are in `live-iitg-vector-parallel-followup-2026-11-07.json`. An opt-in timing run at `a586a80` recorded two completed general extraction requests with 22.0-second and 44.5-second waits to response headers, followed by 2–3 ms to read/parse the response envelope and less than 1 ms for model-content JSON parsing. It still hit the deadline without a sheet. The separate text-page omission audit and other model request kinds were not timed, so the post-extraction stall remains unidentified. The source-hash-bound record is `live-iitg-model-timing-2026-11-07.json`; token counts are provider metadata and no cost estimate is available. Extend request-start and phase telemetry to the text-page audit before optimizing it.

General text extraction now has opt-in request timing through `TCE_MODEL_TIMING=1`. It emits only aggregate batch size/page counts, time to response headers, response-body/envelope parsing duration, model-content JSON parse duration, HTTP status, output character count, and provider token counts when supplied. A whitelist prevents tender text, filenames, document IDs, model content, and credentials from entering these log records. Timing is disabled by default; token counts are not cost estimates, and no raw model payload is retained.

The same timing phases now cover text-page omission audits, including a request-start event with batch index/count. The review progress stream switches to the coverage stage before waiting for each audit wave, so an unfinished audit is visible instead of leaving the prior extraction message as the last status. This indicates work has started but does not imply audit completion; page audit states remain incomplete until validated responses arrive.

The follow-up at `0693e10` ended before reaching the text-page omission audit: two of four general extraction requests completed, but request 3 started at 229.3 seconds and had not received response headers at the 270-second deadline. The five vector pages completed by 214.9 seconds. Progress showed “Parsing the model's extracted technical requirements” while request 3 was still waiting, so its wording did not match the active operation. The content-free source-hash-bound record is `live-iitg-model-timing-followup-2026-11-07.json`; this one run does not establish typical provider latency or a performance regression.

The first isolated post-merge run at `d79857c` used the hash-verified 15-page IIT Guwahati PDF (`88d912e8d3172a99e8422cef2c185dc90692f6b0b1d70e6646f557a524f65967`). It entered vector inspection at 47.2 seconds with five detected pages, left that stage by 224.1 seconds, and reached the 270-second deadline at 271.4 seconds while parsing the text-page extraction result; no response sheet was produced. The monitor retained stage-level timestamps but the implementation did not emit per-page completion updates on its serial fallback, so this run cannot establish whether the vector pages qualified for parallel inspection or attribute a before/after speedup. A follow-up restores page-level progress in that fallback; repeat the run before making a throughput claim. No raw tender/model text, token counts, or cost telemetry were retained.

Page-level visual extraction and its separate image-coverage audit now dispatch in waves of at most the model client's three-request per-analysis limit. This avoids queuing every selected page at once against the 30-second admission deadline and reports progress after each wave. It limits queued work, but does not lower the total request count or guarantee completion before the 270-second analysis deadline.

Independent general text-extraction batches now also run in waves capped at the same three-request per-analysis limit. `Promise.all` results are appended in batch order, and progress advances only after each wave's responses have been parsed. A scripted 12-page upload verifies a peak of three concurrent extraction calls and stable source-ordered requirements. This exercises scheduling and ordering, not live-provider speed, deadline completion, or recall; the IIT Guwahati live timeout still requires reconciliation and may need resumable processing.

The first hash-verified live run after this change completed vector inspection at 228.8 seconds, then started all three general extraction batches together. None received response headers before the 270-second deadline, so omission auditing did not start and no sheet was produced. The source-bound, content-free artifact is `live-iitg-bounded-extraction-followup-2026-11-07.json`. The scripted scheduling guarantee is verified; live-provider throughput and completion remain unresolved, and this single sample is not evidence of a latency improvement.

Opt-in model timings now cover the three calls that make up vector-table page inspection: page-specific column mapping, row classification, and source-row semantic audit. Records include the page/batch index, text/image-independent input character count, request-to-header wait, response parse durations, status, and provider token counts when supplied. They never contain cell text or source identifiers beyond the physical PDF page number. The next live run should use these phase records to identify which work consumes the vector stage's wall time before any heterogeneous-page parallelization changes are considered.

Caught failures in those vector requests also emit an opt-in event with elapsed time and a bounded category (`provider_busy`, `provider_connection`, `request_aborted`, or `other`). The event omits exception messages and response bodies; it distinguishes a failed request from one that simply was not reached before the overall analysis deadline.

The upload stream now enforces a 270-second wall-clock deadline, below the route's 300-second platform limit. On expiry it aborts work through the existing request signal and emits an explicit incomplete terminal error; it never returns already accumulated rows as a finished response sheet. This bounds one request and prevents a platform timeout from silently looking like success. It is not resumable processing: completed batches are not persisted, and the reviewer must retry a shorter tender. A future resumable design must checkpoint source-linked batch results and preserve per-page/audit completeness states before it can safely return partial work.

The vector-table coverage ledger also carries each detected row's table/row/cell IDs and the IDs of accepted requirements linked to that row. The link status reports only whether any requirement is associated with the row; candidate and accepted requirement counts remain visible as separate counts. A separate bounded model pass compares each requirement-classified source row with its extracted quotes and reports `no_gap_reported`, `possible_gap`, `ambiguous`, or `audit_incomplete`. Inputs are limited to 12 rows and 12,000 characters per request, with at most 16 requests per analysis; oversized rows and work beyond that budget are explicitly marked incomplete. Statuses are retained for every detected row even though the UI shows only the first twelve details per page. The audit is advisory and never asserts completeness. All nonempty rows remain visibly unresolved, including rows where the audit reports no gap, because this same-model pass is not ground truth.

The row audit may now return up to eight exact, contiguous source-cell excerpts for a `possible_gap`. A deterministic validator rejects paraphrases, joined-cell text, overlong outputs, and excerpts attached to any other disposition. Accepted excerpts re-enter as separate candidate rows and still pass the ordinary source-text grounding and numeric validation ladder; they remain unchecked for human review. This provides a bounded recovery path from an advisory finding, not independent proof that the audit found every omission. If the model cannot quote an exact excerpt, the row remains flagged without an automatic candidate.

Detected vector-table rows retain an advisory structural class and a reason code. Rows the classifier marks ambiguous do not generate requirements; they remain visible in the coverage ledger with their source text and an explicit unresolved classification. Header/instruction exclusions are likewise visible as source rows with their class and reason. These labels guide human review and are not ground truth; a linked requirement still does not prove that every obligation in a row was extracted.

The next engineering steps are:

1. Make inventory construction explicit and independently inspectable, retaining native text, OCR regions, raster image regions, and page geometry for hybrid pages. The current step records approximate PDF.js image draw bounds and exposes them for human page review; semantic region classification and canonical section/paragraph/list relationships remain open.
2. Compare the current PDF.js/vector reconstruction with optional parsers on adjudicated regions, not aggregate table counts alone.
3. Rework extraction around bounded, resumable page/region batches and explicit incomplete states; the current stream-level deadline stops overlong work but cannot resume it or return partial results.
4. Represent each independently answerable obligation as an atomic proposal and preserve all source locations through review and export.
5. Add independently annotated golden and held-out tenders before changing parser defaults or claiming improved recall.

The first direct production-parser comparison now runs PDF.js against the existing PyMuPDF shadow inventory on the six local, hash-verified PDFs. Page dimensions, image-region counts, and summed image-area ratios matched on all 183 pages; vector operator counts are intentionally not compared as equivalent table evidence. Text segmentation metrics are retained side by side without a numeric diff because their APIs use different boundaries and whitespace conventions. This is a parser inventory parity observation only; per the benchmark record it does not establish table fidelity, semantic completeness, or generalization. Continue with adjudicated region/table comparisons before changing production parser behavior.

A separate geometry-only run on the held-out IIT Guwahati tender compares PyMuPDF table candidates with 23 assistant-reviewed source bounds. `lines`/`lines_strict` envelopes fully cover the seven annotated specification-table spans on page 11 but none of the 13 narrative/documentary spans on pages 2–4. The `text` strategy covers almost every bound only by returning broad candidates (median candidate area about 28 times the annotated source area). This supports retaining complementary structural and narrative extraction paths; it does not support treating table bounds as semantic coverage. Independent human adjudication and candidate-level extraction comparisons remain open.

A fresh live run of the current pipeline on the 15-page IIT Guwahati tender completed in 186 seconds, selected six pages, and returned 96 unchecked source-matched rows. Nine pages were unrouted, nine did not receive the page-level completeness audit, and the six audited pages reported no possible gaps. Exact source anchors matched all anchors in four of 23 partial annotation cases; three of seven page-11 groups previously recorded as omissions still lacked matching anchors. This demonstrates that the existing selected-page and same-model audit path does not establish completeness. The run is one nondeterministic sample with no cost telemetry; do not compare its row count with the earlier 114-row run as a before/after result because exact prior rows and conditions are unavailable.

## Parser evaluation and licensing

PyMuPDF 1.26.5 was run in shadow mode on the six local samples. Its `lines` candidate counts were broadly similar to the current vector detector on several documents and differed substantially on the Indore sample. Its `text` strategy generated table candidates on nearly every text-bearing page, which illustrates why raw candidate count is not a quality metric. The scanned Shah sample had no native text for PyMuPDF to recover. These results do not establish precision or recall, and do not justify switching production parsers.

Do not add PyMuPDF as a product dependency in this ADR. [PyMuPDF's licensing documentation](https://pymupdf.readthedocs.io/en/latest/about.html#license-and-copyright) describes its AGPL and commercial Artifex licensing options; adoption requires a licensing decision in addition to measurable gains on representative, adjudicated layouts. Evaluate Docling or other parsers under the same held-out, source-linked protocol before adding them. Keep parser experiments optional and isolated from runtime dependencies.

## Guarantees and boundaries

- Preserve source text and OCR as distinct evidence. OCR never silently overwrites the native transcript.
- Unknown page, clause, cell, confidence, or geometry values stay unknown; approximate coordinates remain labelled approximate.
- Keep independent obligations independently answerable. Only verified continuations of one obligation and presentation headings may merge.
- Evaluate source grounding, extraction completeness, and response/export fidelity as separate guarantees.
- Keep Phase 2 OEM ingestion, retrieval, compliance assessment, contradiction resolution, and submission generation out of scope.
- Do not claim unattended customer-ready output based on selected-page extraction or a partially completed run.

## Consequences

The current TypeScript runtime and local OCR tools remain in place while evidence is gathered. More explicit inventory and batch contracts will require incremental refactoring of `actions.ts`. The single-user deployment still lacks a cross-instance quota; process-local counters would not provide a global guarantee. A future shared-state or deployment-level control must be chosen before representing global spend limits as implemented.

The baseline and first adjudicated cases are tracked in [`../../benchmarks/representative-tenders/README.md`](../../benchmarks/representative-tenders/README.md). They are a starting subset, not a full benchmark or an unbiased held-out evaluation.
