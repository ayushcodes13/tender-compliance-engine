# CP24: Processing retry, idempotency, and per-page-error visibility

Closes the remaining CP24 gaps that were identified during analysis. The
version-level state machine, deterministic `run_id`
(`make_job_id(version_id, stage)`), idempotent `store_pages`
(delete-then-recreate), and `FAILED/PARTIAL → QUEUED` transitions already
existed on `main`; CP24 adds the retry **action**, the retry **API**, and
**per-page error visibility**.

## What changed

### `DocumentService.requeue_version` (`apps/api/src/tender_compliance_api/document/service.py`)
- Transitions a `FAILED`/`PARTIAL` version back to `QUEUED` and returns the
  deterministic PARSE `run_id`.
- **Idempotent**: a version already `QUEUED`/`PROCESSING` returns the same
  `run_id` without re-transitioning (so firing retry twice enqueues one
  deterministic job — queue-side dedup handles the duplicate).
- **Rejects terminal states**: `PARSED` raises `TransitionError` (409 at the
  API). Retrying a completed version is a new upload/version, not a silent
  re-run of the same source.
- Tenant-isolated via `get_version_or_raise`; audit-logged as
  `document.retry` with from/to status + run_id.
- **Source bytes are never mutated or destroyed**: `DocumentVersion` and its
  `StoredObject` (FK `RESTRICT`) are reused unchanged — retry is explicitly
  *not* a new source version (checkpoint guardrail).

### `POST /projects/{project_id}/documents/{document_id}/versions/{version_number}/retry`
(`apps/api/src/tender_compliance_api/routes/uploads.py`)
- Thin route mirroring `upload_document`'s dependency shape
  (`auth` + `session` + `queue`). Delegates to `requeue_version` then
  enqueues the deterministic PARSE job (`attempt=1`).
- Returns `RetryResponse { run_id, status }`.
- 404 for missing document/wrong-project (no version enumeration), 409 for
  terminal `PARSED`.

### Per-page error visibility (`DocumentService.store_pages`, same file)
- `PageResult.error` is now persisted into `structural_metadata["error"]`.
  A single failed page never silently disappears inside an otherwise-
  successful parse (CP19 `extracted_text` is still `None` for empty pages;
  the cleanup split is unchanged). Widened `meta` type to `dict[str, Any]`.

## Schema / data impact
No new migration. `structural_metadata` is a JSON column (used since CP23);
the `error` key is a new optional key. `requeue_version` and the retry route
are service/route only.

## Risks / limitations
- Operator retry re-runs the **full** PARSE→OCR→CLEANUP→EXTRACT pipeline
  with a fresh worker `attempt` (reset to 1). `ProcessingRun.attempt` is the
  per-version-per-stage max+1 (auditable in the runs table). This is the
  intended "reprocess from scratch" semantics for an operator who has since
  fixed the source/credentials.
- Retry does not yet expose per-page error **diagnostics** in the API
  response (the `GET .../pages` detail view is a future checkpoint).
