## Phase 1 v2 corpus and leakage policy

`../phase-1-v2-corpus.json` fingerprints all 11 PDFs currently under `examples/`. Every repository example is assigned to **development** because this pool has informed prior analysis and engineering. The two PGIMER model-tender files share one family group; their byte hashes differ, so the inventory does not claim they are identical. The previously used Madras and IIT Guwahati tenders are also development data even though an older artifact calls the latter held out. There is currently no independent validation or locked evaluation set.

Recheck the repository inventory with `node benchmarks/scripts/verify-phase1-v2-corpus.mjs`. It verifies file membership, SHA-256, byte counts, physical page counts, and counts pages with selectable text using `pdfinfo` and `pdftotext`. It prints counts only and stores no extracted tender text. A text-bearing page can still contain scanned tables or image-only regions; these counts do not establish native/scanned/hybrid coverage, table detection, obligation recall, or document completeness. The inventory reports 367 physical pages, 234 pages with selectable text, 11 unique byte fingerprints, and 10 family groups. Source/layout classification, complete annotations, and a true locked evaluation set remain open work.

The page-level PDF.js signal inventory is reproducible with `node --experimental-strip-types benchmarks/scripts/inventory-phase1-v2-pages.mjs --output benchmarks/phase-1-v2-page-inventory.json`. It reuses the production PDF.js, image-region, vector-row, heading-candidate, and OCR-routing helpers. It stores only per-page counts/booleans and aggregate candidates, never source text or bounding boxes, and executes neither OCR nor model calls. Its current run reports 232 pages with selectable text by PDF.js, 166 pages with raster-image signals, 31 with both text and raster signals, 126 with vector-table geometry candidates, 73 with vector-row candidates (744 candidate rows), 28 simple native annexure-heading candidates, four simple technical-heading candidates, and 145 pages for which the current OCR helper recommends OCR. Only seven image regions were selected by the helper on pages that also have native text; scan-only pages use the page-level OCR path. These are parser/routing diagnostics, not region coverage or accuracy measures. The earlier Poppler inventory reports 234 text-bearing pages: the difference is exactly the two PGIMER copies, where Poppler extracts text on physical page 61 but PDF.js exposes no native text on any page. PDF.js reports raster signals and recommends page OCR for all 61 pages in each copy. Treat this as parser disagreement, not proof that the source content is missing. The artifact records eight PDF.js warnings during the run.

### Actual local OCR dispositions and structural inventory

Run the source-free disposition pass with:

```sh
node --experimental-strip-types benchmarks/scripts/characterize-phase1-v2-layout.mjs \
  --output benchmarks/phase-1-v2-layout-characterization.json
```

This pass uses PDF.js 4.10.38, Poppler `pdftoppm` 26.10.0, and Tesseract 5.5.3 (`eng`) from the current local environment. It follows the production routing/OCR decisions with the same 120-page, 210-second, six-image-region, and 1700-pixel limits per PDF. It builds and validates the production `SourceDocumentModel` shape in memory. The artifact stores no native/OCR text, coordinates, bounding boxes, or model payloads; it contains only page/region states, counts, parser candidates, and validation issue codes. A second full run was byte-identical in this environment.

Across 367 pages, the current pass reports: 222 pages not recommended for OCR; 143 pages with some OCR text; two pages where OCR found no text; and zero recommended pages left unattempted or failed. Those 145 recommendations used full-page OCR on 140 pages and selected image-region OCR on five pages. Seven image regions were selected: four found OCR text and three did not. The other 8,248 detected image operators are recorded as not targeted; this includes image operators on scan-only pages where full-page OCR is used and is not linked back to each image operator. `validateSourceDocumentInventory` reported zero structural issues across the 367 assembled pages. The parser produced 126 vector-table-geometry pages, 744 candidate rows, and 1,546 candidate cell-text slots.

These are execution and parser diagnostics. “Text found” does not mean OCR is correct, confidence is not accuracy, and a valid source inventory does not establish that every meaningful region/table/obligation was detected. A coarse thumbnail-scale visual skim has now covered all 367 physical pages, but table/cell verification, cross-page continuation, and annexure linkage remain incomplete. The V2.1b2 checkpoint therefore remains open.

## Reading the baseline

The six documents contain 183 PDF pages. The current PDF.js/vector-table path and PyMuPDF `find_tables` strategies were compared in shadow mode. Counts are candidate geometry statistics only; they do not measure correct table detection. No OCR was run in the PyMuPDF comparison. The Shah document is image-only and therefore has no selectable text for either parser to interpret without OCR.

The configured local model path completed 2 of 6 analyses within a 295-second client limit. Three calls reached that limit while extracting, and the scanned Shah run failed at the application time limit. The two completed matrices are not recall results: many pages were not selected or omission-audited. The captured outcomes contain no cost telemetry. Do not use these results to claim quality or production capacity.

- PDF.js and the production vector-table parser are in `apps/web`; run the repository's documented Node test/runtime commands with the pinned lockfile.
- PyMuPDF 1.26.5 was installed only in the local evaluation environment; it is not a runtime or development dependency of the product.
- Re-run the PyMuPDF shadow inventory with `python3 benchmarks/scripts/pymupdf-shadow.py id=/absolute/path/to/file.pdf ...`. It emits fingerprints, timings, parser counts, and source-region geometries, but never source text. Use the same version when comparing recorded results.
- Recheck held-out source-anchor artifacts against the manifest PDF with `node benchmarks/scripts/verify-golden-anchors.mjs --source /absolute/path/to/iitg-utm.pdf --annotation benchmarks/representative-tenders/heldout-golden-v0.4.json --annotation benchmarks/representative-tenders/heldout-golden-v0.5.json --annotation benchmarks/representative-tenders/heldout-golden-v0.6.json`. - The model run used the configured local provider, whose secret is deliberately not recorded. The 295-second client limit is part of the run conditions, not a provider SLA.
- Do not commit source tenders, full extracted document text, credentials, or provider request/response dumps.

### Source-obligation golden reconciliation

`node benchmarks/scripts/evaluate-source-obligations.mjs --annotation benchmarks/representative-tenders/heldout-golden-v0.6.json --output /secure/local/path/saved-analysis.json --trace /secure/local/path/forensic-trace.json` compares each annotated source anchor against the matching physical page's `requirements[].sourceReference.sourceText` and, when supplied, candidate source quotes/dispositions from the forensic trace. The saved analysis must include its tender fingerprint as `document.documentFingerprint` (or the wrapper may provide `sourceSha256`) and saved requirements; the trace must carry the same document fingerprint. The evaluator accepts either a saved analysis object or an `{ analysis: ... }` wrapper. Keep source-containing artifacts in an access-controlled local location; do not commit them. The result reports source anchors covered, partially covered, or without a matching citation, lists matching requirement IDs, and distinguishes trace candidates recorded as rejected/duplicate/etc from anchors with no matching source-quoted candidate. `not_generated` means no such candidate was recorded; it does not prove the model never considered the obligation. It does not use audit suggestions or `no_gaps_reported` fields as evidence. It measures source-anchor citation coverage only, not semantic interpretation, obligation completeness, or recall over unannotated pages.

`benchmarks/fixtures/iitg-page11-synthetic-output.json` and `benchmarks/scripts/evaluate-source-obligations.test.mjs` exercise all seven page-11 annotation groups with synthetic rows. The fixture intentionally reports `no_gaps_reported` while leaving the three previously missed obligations unmatched; the test asserts the source-obligation result instead of trusting that model audit claim. The saved IIT Guwahati run still cannot be evaluated row by row because its requirement text and citations were not retained. Do not infer its historical row-level performance from the synthetic fixture or aggregate counters.

## Limitations

The set is small and convenience-sampled, not statistically representative. The current annotations are partial and not independently adjudicated. The original six-document model run timed out or failed on four documents, does not include token/cost telemetry, and cannot support a recall comparison. The IIT Guwahati analysis completed but nine pages were not omission-audited and all 114 output rows require human review. The public source did not state a reuse license; the source PDF is therefore kept local and not redistributed. Whole-tender application of the protocol, independent adjudication, and more independent public tenders remain necessary.
