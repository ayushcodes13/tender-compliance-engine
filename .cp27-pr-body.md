# CP27: Chunking, overlap, clause hierarchy, tables, and multi-page windows

## Why
CP26 added the LLM adapter seam; CP28 will call it to extract requirement
candidates. But the model must receive **bounded, context-rich** windows — not
arbitrary token slices — so it can understand complicated tender structure
(nested clauses, tables, multi-page requirements) without losing provenance.
CP27 introduces a pure, deterministic chunker that turns a version's parsed
`DocumentPage` rows into source-anchored `SourceWindow` fragments the EXTRACT
stage can iterate over.

## What changed
- New pure module `extraction/chunking.py`:
  - `SourceWindow` (frozen dataclass): `chunk_id`, `text`, `sources`
    (tuple of `TrustedSourceContext`, one per contributing page), `overlap`
    (bounded tail of the previous window's text), `hierarchy` (clause path
    deepest-last), `table_context` (preserved table header labels).
  - `build_source_windows(pages, *, organization_id, document_id,
    max_chars=1500, overlap_chars=150)` — deterministic chunker.
- **Boundaries (never flattening):** windows break only *between* atomic
  segments.  Segments are: clause headers (singleton, detected with the same
  numbered-clause regex as `parser.cleanup`), table blocks (consecutive `|`
  rows kept together, header row recorded), and paragraph blocks (consecutive
  non-blank lines; blank lines flush a segment).
- **Bounded overlap (CP27.2):** each window after the first carries
  `overlap` = the previous window's last `overlap_chars`; recorded (not
  silently merged) so CP29 can collapse duplicates predictably.
- **Stable chunk IDs (CP27.3):** content-addressed to version + page span +
  char span + clause + content hash → identical input yields identical windows.
- **Honest multi-page provenance (CP27.6):** a window spanning pages carries a
  `TrustedSourceContext` (EXACT char offsets within that page's `cleaned_text`)
  for **every** contributing page, so a multi-page requirement is never
  detached from any of its locations.  Source pages are the real input pages —
  no synthetic page numbers or version ids (AGENTS: "never fabricate").
- **No data loss:** a single atomic segment larger than `max_chars` is still
  emitted whole (validated params: `max_chars>0`, `0<=overlap<max_chars`).
- `SourceWindow` / `build_source_windows` re-exported from `extraction`.

## Scope
Included: CP27 chunking layer + tests.  Excluded: any processor/DB change —
the EXTRACT stage still no-ops (CP28 wires `build_source_windows` around the
LLM call).  No Alembic migration (pure in-memory windowing).

## Provenance / evidence impact
- `chunk_id` is deterministic, so operators can explain which window fed which
  extraction (auditability; AGENTS "keep business logic testable").
- Every `SourceWindow.sources` fragment is `TrustedSourceContext` with EXACT
  per-page char offsets — no model-supplied page/window fields can override
  provenance.
- `overlap` is explicit, so CP29's duplicate reconciliation can detect it.
- No document bodies / citations / compliance verdicts are stored (Phase 1).

## Risks / limitations
- Clause detection reuses the cleanup numbered-clause regex as a heuristic;
  it is conservative (matches `1`, `1.2`, `1.2.3` styles).  Ambiguous
  non-numeric clause styles (e.g. "Annex A") are treated as paragraphs — they
  still chunk correctly, just without a hierarchy entry.  A future structured
  parser can supply explicit clause boundaries without changing the chunker.
- `max_chars` is a char cap (not tokens); CP28 will translate the budget to
  the chosen model's tokenizer as needed.
- No processor wiring in this PR; `build_source_windows` is exercised by tests
  only until CP28 calls it.
